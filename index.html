01 — Lab Environment

An isolated range, built to fail safely

Metasploitable 2 (an intentionally vulnerable, End-of-Life Ubuntu 8.04 build) and Kali Linux were deployed in Oracle VM VirtualBox on a private Host-only network — sealed off from the host and the internet, with a NAT network switched in only for brief, controlled package downloads.

04 — Hardening Strategy

Three phases, mapped to MITRE D3FEND

Every action ties to a defensive technique in the D3FEND framework — from immediate containment through to OS-level exploit mitigation.

PHASE 01

Immediate Containment

Eliminate any active backdoor offering a direct, unauthenticated path to root.

  • Stop & purge vsftpd, UnrealIRCd, Telnet
  • Remove services from boot sequence
  • D3-ACH
PHASE 02

Secure Baseline

Establish foundational controls across the network and credential layers.

  • Default-deny iptables firewall
  • Password complexity & aging policy
  • D3-SCP · D3-SPP · D3-CFP
PHASE 03

System & Service Hardening

Harden remaining essential services and system-level exploit resistance.

  • SSH: disable root login, move port, Fail2Ban
  • Enable full ASLR (kernel.randomize_va_space=2)
  • D3-ACH · D3-SAOR
D3-SU Software Update D3-ACH Application Config Hardening D3-SCP System Config Permissions D3-SPP Strong Password Policy D3-CFP Change Default Password D3-SAOR Segment Address Offset Randomisation

Default-credential & dictionary attack (Medusa)

kali@kali — medusa 
$ medusa -h 192.168.56.101 -u msfadmin -P rockyou.txt -M ssh -n 2222
ERROR: Cannot connect [unreachable]
$ medusa -h 192.168.56.101 -u postgres -p postgres -M postgres -n 5432
NOTICE: port 5432 was not open

Default credentials on SSH, PostgreSQL and MySQL all failed — the changed passwords held, and the default-deny firewall blocked the database ports outright before credentials were even tested.

ASLR runtime verification

A custom C program printed a stack variable's memory address across three consecutive executions post-hardening — each run returned a different address, confirming kernel.randomize_va_space = 2 is actively randomising memory layout at runtime.

Run 1 — 0xbf954eb0 Run 2 — 0xbf828d80 Run 3 — 0xbfaa5000
07 — Challenges & Learning Points

Hardening a dead OS teaches you where real defense lives

Patching alone proved insufficient — the real work was in compensating controls.

Patching hit a wall

The old-releases archive provided almost no meaningful security updates for an EOL OS — confirming that service removal, firewalling and credential hardening had to carry the defense, not patches.

SSH algorithm mismatch

Modern clients refuse the target's legacy ssh-rsa/ssh-dss host keys by default — every verification step needed an explicit client-side override to even connect.

Lynis false positive

Lynis misread a populated iptables ruleset as empty on this legacy build — a reminder to corroborate automated audit output with direct iptables -L checks.

Aging didn't apply retroactively

Global password-aging settings in /etc/login.defs only bound new accounts — existing users needed explicit chage enforcement.

Silent PAM failure

A single misplaced line in common-password caused passwd to report success while silently not saving the new hash — only caught during verification.

Snapshots as a safety net

VirtualBox snapshots turned risky, irreversible-feeling changes into a fast "implement → verify → restore" loop on a fragile legacy system.

08 — Conclusion

A robust baseline — not a finish line

Compensating controls carried the defense

Layered hardening under the MITRE D3FEND framework closed every publicly known backdoor, stood up a default-deny firewall, remediated credential weaknesses, and enabled full memory-layout randomisation — each independently verified through adversarial testing, not just configuration review.

A production equivalent of this system would still need migration off an End-of-Life OS, continuous monitoring, and application-layer remediation (e.g. the web services) to reach comprehensive, long-term security.
